Practice Service

📋 Resumen de Interacción

Intercambio bidireccional clave: asistencia sincrónica del tutor socrático (< 2s) y evaluación asincrónica del uso de IA por Kafka.

📑 Contratos con este Micro

Canal Sincrónico (HTTP REST) POST /api/llm/tutor/interactions
POST /api/llm/tutor/conversations
Canal Asincrónico (Kafka Event Bus) Consume: intento_cerrado.v1
Publica: score_de_ia_calculado.v1

📤 Qué se necesita enviar

Token M2M (aud=llm-service), Header Idempotency-Key (UUID), attemptId, challengeId, courseCohortId, learnerId, mensaje del alumno y riskLevel.

ℹ️ Ficha Técnica de Integración

⏱️ Presupuestos de Latencia

Tutor: Máximo 2 segundos de punta a punta. Incluye AI Gateway determinístico (5-50ms), RAG retrieval pgvector (<100ms), llamada al modelo (~500ms) y Guard Anti-Fuga.
Evaluador: Asincrónico por cola/Batch (-50% costo). El alumno no espera en pantalla.

🛡️ Resiliencia y Degradación

Si el modelo primario falla, actúa la escalera de degradación (Nivel 1 al 4). Si se agotan los reintentos en <2s, devuelve state: "unavailable".

🛡️ Reglas Transversales de Borde y Mensajería Estándares de Plataforma
1. El API Gateway es la Única Puerta

Nadie llega directo a llm-service. Todo request pasa por el API Gateway bajo el prefijo /api/llm/** con validación obligatoria de JWT M2M (aud=llm-service).

2. Correlación Distribuida en Headers

Tanto llamadas HTTP como eventos Kafka deben propagar los headers traceparent (W3C standard) y X-Request-Id. Los cuerpos JSON nunca deben incluir campos trace_id.

3. Idempotencia en Escrituras

Toda llamada POST/PUT de mutación exige el header Idempotency-Key: <UUID>. Las respuestas se almacenan en la tabla idempotency_requests para devolver el mismo resultado ante reintentos.

4. Errores RFC 7807 (Problem Details)

Todas las respuestas de error 4xx y 5xx devuelven un objeto estandarizado con type, title, status, detail e instance.
