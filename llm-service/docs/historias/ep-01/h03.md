## Notas / Observaciones

- **Reglas de negocio:** el servicio se registra en Eureka como `llm-service`; el Gateway rutea
  `/api/llm/**` sin reescritura de path; la seguridad M2M (entre servicios, sin usuario humano de
  por medio) valida `aud=llm-service` y el scope requerido; los errores se devuelven como
  *Problem Details* (RFC 7807).
- **Validaciones:** se propaga la correlación `traceparent` y `X-Request-Id` en cada respuesta; un
  token sin el scope necesario se rechaza con `401`; una identidad delegada falsificada o mal
  formada se rechaza con `403`.
- **Datos obligatorios (headers de borde):** `X-Service-Id`, `X-Service-Scopes`,
  `X-Delegated-User`, `X-Request-Id`, `traceparent`.
- **Performance:** el *health* de Actuator responde sin llamar a proveedores externos.
- **Seguridad:** ningún endpoint funcional queda accesible sin pasar por el Gateway; los logs no
  registran tokens.
- **Accesibilidad:** no aplica.
- **Otros:** el pipeline de CI del servicio queda en verde (build, pruebas, cobertura).
- **Endpoints expuestos en esta historia:** `GET /actuator/health` (liveness/readiness) y la ruta
  base `/api/llm/**` protegida; las operaciones de golden set llegan en H05/H06.

## Criterios de Aceptación (CA)

- [ ] **CA1:** `llm-service` aparece registrado en Eureka y responde a través del Gateway en
  `/api/llm/**`.
- [ ] **CA2:** una request con token M2M válido (`aud=llm-service`) y scope correcto obtiene respuesta
  y recibe de vuelta su `X-Request-Id`.
- [ ] **CA3:** los errores se serializan como *Problem Details* con `type`, `title`, `status` y
  `detail`.
- [ ] **CA4 (negativo):** token sin el scope requerido → `401` *Problem Details*.
- [ ] **CA5 (negativo):** header de identidad delegada ausente o falsificado → `403`.
- [ ] **CA6:** el pipeline de CI del servicio está en verde.

## BDD

**Característica:** borde transversal del `llm-service`.

### Escenario 1 — Integración contra un borde estable

- **Dado:** `llm-service` registrado en Eureka y el Gateway ruteando `/api/llm/**`
- **Cuando:** un servicio consumidor llama con token M2M válido y scope correcto
- **Entonces:** recibe una respuesta del servicio
- **Y:** la respuesta incluye el mismo `X-Request-Id` que envió

### Escenario 2 — Token sin scope

- **Dado:** un servicio consumidor con un token M2M válido pero sin el scope requerido
- **Cuando:** llama a una ruta `/api/llm/**`
- **Entonces:** recibe `401` con cuerpo *Problem Details*

### Escenario 3 — Identidad delegada falsificada

- **Dado:** una request que trae un `X-Delegated-User` que no vino del Gateway de confianza
- **Cuando:** llega al servicio
- **Entonces:** se rechaza con `403` y no se ejecuta ninguna acción

## Dependencias / Impactos

- **Servicios involucrados:** Gateway, Eureka, emisor de tokens M2M.
- **Módulos afectados:** `api`, `security`, `configuration`.
- **Otros equipos / aprobaciones:** equipo de Gateway/Discovery (D01): ruta, `aud` y scopes.
- **Impacto en datos / migraciones:** ninguno.
- **Riesgos y mitigación:** el contrato de headers del Gateway puede cambiar; se aísla en el
  módulo `security` y se cubre con pruebas de contrato (WireMock).
- **Estrategia de autonomía (mientras D01 no tenga Gateway/Eureka/emisor M2M reales disponibles
  para integrar):**
  - **WireMock** simula al Gateway inyectando `X-Service-Id`, `X-Service-Scopes`,
    `X-Delegated-User`, `traceparent` y `X-Request-Id` en los tests de contrato (CA2/CA4/CA5).
  - **`FakeJwtIssuer`** bajo perfil Spring `local`/`test`: emite JWT `aud=llm-service` con scopes
    configurables, firmado con clave simétrica de test (nunca la real); expone
    `/test-support/token` solo bajo ese perfil.
  - **Eureka:** `eureka.client.enabled=false` en `test`; en `local`/CI se registra contra el
    Eureka Server OSS levantado en H02.
  - Ninguna de estas piezas cierra la historia por sí sola: la demo de S1 exige integración real
    contra D01 antes de dar CA1/CA2 por definitivamente cumplidos (regla del DoR, ítem 7).
