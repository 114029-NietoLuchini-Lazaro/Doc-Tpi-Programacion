## Descripción (Como / Quiero / Para)

- **Como:** la plataforma
- **Quiero:** implementar `ModelInvocationPort` contra un proveedor real de modelos (vía
  `langchain4j`, según ADR-016), activable con una clave de API, sin tocar a ningún consumidor
  del puerto
- **Para:** que la invocación del modelo deje de ser simulada en cualquier función que ya use el
  puerto — tutor, calibración, evaluador y RAG lo heredan sin cambiar una línea propia

> **Nota de tipo:** tarea interna — el rol no lo protagoniza un usuario final, así que falla la
> **V** de INVEST a propósito (ver "Tipo" en el encabezado).

## Notas / Observaciones

- **Reglas de negocio:** el nuevo adaptador implementa la misma interfaz `ModelInvocationPort`
  que ya usa `FakeModelAdapter`; ningún consumidor (`ModelInvocationService` y todo lo que corre
  detrás) se entera de cuál está activo. Cuál adaptador corre para cada función se sigue
  decidiendo por fila de `function_model_config` (ya construido en `LLM-S01-H10`) — **nunca** se
  hardcodea en código ni se redespliega para cambiarlo.
- **Validaciones:** timeout configurable y error controlado (`ModelTimeoutException`, mismo
  mecanismo que ya valida `LLM-S01-H10`·T4), y validación de la respuesta contra el
  `ModelResponseSchema` de la función invocada — una respuesta fuera de schema se trata
  exactamente igual que hoy con el fake, no se relaja el contrato por ser un proveedor real.
- **Datos obligatorios:** la clave de API del proveedor viaja por variable de entorno, nunca
  versionada (regla ya vigente del ADR de S1) — un despliegue sin la variable configurada para
  una función que la necesita falla explícito, no en silencio.
- **Performance:** el free tier del proveedor es la referencia de costo — ADR-010/ADR-006 ya
  fijan ese criterio; esta historia no cambia esa decisión, solo la implementa.
- **Seguridad:** ninguna credencial de proveedor queda en el repositorio, en ningún commit — el
  mismo caso que ya obligó a rotar la key de la demo vieja (`E08-06`/`LLM-...` histórico). **Hasta
  que [08 · C-2](../../08-decisiones-y-pendientes.md#-c-2--el-free-tier-puede-tocar-datos-de-alumnos)
  se resuelva, las pruebas contra el proveedor real usan únicamente datos sintéticos o del golden
  set — nunca transcripciones reales de alumnos** (recomendación explícita de C-2, todavía 🔴).
- **Accesibilidad:** no aplica (sin pantalla).
- **Otros:** correr por primera vez el conjunto de pruebas ya existente de todo lo que consume el
  puerto (`FakeModelAdapterTest`, `ModelInvocationServiceTest`, `TutorInteractionServiceTest`,
  `CalibrationEvaluationRunnerTest`, `RagChatServiceTest`, etc.) **contra el adaptador real**, al
  menos una vez, antes de dar esto por cerrado — hoy todos corren únicamente contra el fake.

## Criterios de Aceptación (CA)

- [ ] **CA1:** con la variable de entorno de la API key configurada, invocar una función cuyo
  `function_model_config` apunta al proveedor real devuelve una respuesta generada de verdad (no
  simulada), validada contra el schema de esa función.
- [ ] **CA2:** cambiar la fila de `function_model_config` de una función del fake al proveedor
  real (o viceversa) no requiere tocar código ni redesplegar.
- [ ] **CA3 (caso que debe fallar):** una respuesta del proveedor que no valida contra el schema
  esperado se trata como error controlado — no se propaga texto crudo a ningún consumidor.
- [ ] **CA4 (caso que debe fallar):** si el proveedor no responde dentro del timeout configurado,
  la invocación falla con `ModelTimeoutException`, igual que hoy ante el mismo caso simulado.
- [ ] **CA5 (caso que debe fallar):** arrancar el servicio con una función asignada al proveedor
  real pero sin la variable de entorno de la API key configurada falla de forma explícita al
  intentar usarla, nunca en silencio ni con una respuesta vacía.

## BDD

**Qué se prueba:** que el puerto de invocación funcione igual de bien con un proveedor real que
con el fake, y que un problema del proveedor (respuesta inválida, timeout, credencial ausente) se
controle exactamente como ya se controla hoy.

### Escenario 1 — Invocación real dentro de tolerancia (camino feliz)

- **Dado:** una función con `function_model_config` apuntando al proveedor real y su API key
  configurada
- **Cuando:** se invoca esa función con un prompt válido
- **Entonces:** se recibe una respuesta generada por el proveedor, validada contra el schema
  esperado

### Escenario 2 — Respuesta fuera de schema

- **Dado:** el proveedor real responde con un formato que no cumple el schema de la función
- **Cuando:** el puerto valida la respuesta
- **Entonces:** se rechaza como error controlado, sin propagarse al consumidor

### Escenario 3 — Credencial ausente

- **Dado:** una función asignada al proveedor real sin su variable de entorno configurada
- **Cuando:** se intenta invocarla
- **Entonces:** falla de forma explícita, con un mensaje que identifica la causa — no una
  respuesta vacía ni un `500` genérico

## Dependencias / Impactos

- **Partes involucradas:** `domain/ai/ModelInvocationPort`, `ModelInvocationService`,
  `function_model_config` (todo ya construido en `LLM-S01-H10`); librería `langchain4j`.
- **Otros equipos / aprobaciones:** ninguna — es enteramente interno a `llm-service`.
- **Impacto en los datos:** ninguno nuevo — reutiliza `function_model_config`, solo agrega filas
  o actualiza las existentes para apuntar al proveedor real.
- **Riesgos:** un proveedor real se comporta distinto del fake en casos borde (latencia real,
  rate limiting del lado del proveedor, formatos de error propios) — correr la suite existente
  contra él (ver "Otros" arriba) antes de dar por cerrada cualquier historia que dependía
  únicamente de haber sido probada contra el fake.
