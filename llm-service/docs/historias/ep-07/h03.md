## Descripción (Como / Quiero / Para)

- **Como:** sistema (tarea habilitadora — falla el criterio V de INVEST porque no tiene un usuario final directo)
- **Quiero:** que todas las rutas del servicio que están sujetas a cuota devuelvan HTTP 429 con la cabecera `Retry-After` cuando se supera el límite diario configurado, y que los reintentos internos al proveedor usen backoff exponencial con jitter y circuit-breaker
- **Para:** proteger el presupuesto del proveedor de modelos y dar al consumidor la información suficiente para reintentar de forma controlada sin saturar el sistema

---

## Notas / Observaciones

- Las rutas sujetas a cuota son: `POST /api/v1/tutor/message`, `POST /api/v1/evaluations` (evaluación síncrona), `POST /api/v1/evaluations/async` (evaluación diferida), `POST /api/v1/rag/ingest`. Cualquier ruta nueva que llame al proveedor debe registrarse en el `QuotaRegistry`.
- El contador de cuota se evalúa **antes** de llamar al proveedor. Si supera el límite: se devuelve 429 sin llamar al proveedor.
- La cabecera `Retry-After` indica los segundos hasta la medianoche UTC (inicio del siguiente período de cuota diario). Formato: entero en segundos (`Retry-After: 3600`).
- El body del 429 incluye: `{"error": "quota_exceeded", "function": "<nombre>", "retryAfter": <segundos>, "resetAt": "<ISO-8601>"}`.
- Reintentos internos al proveedor (errores 5xx del proveedor): backoff exponencial con jitter, máximo 3 reintentos, cap de 8 segundos. No aplica a errores del consumidor (4xx).
- Circuit-breaker por función: si > 50 % de llamadas a una función fallan en 60 segundos → circuito abierto, todas las llamadas a esa función reciben 503 con `{"error": "circuit_open", "function": "<nombre>", "retryAfter": 30}` durante 30 segundos antes de intentar half-open.
- Métricas: cada 429 emitido y cada apertura de circuito se registra en `llm_usage_metrics` para que el panel (LLM-S09-H01) lo refleje.
- El middleware de cuota es transversal y se aplica vía `QuotaFilter` en la cadena de filtros de Spring Security (orden: autenticación → autorización → cuota → handler).
- Si el alumno que hace la llamada tiene un override de `scope=student` vigente (ver [h02.md](h02.md)), `QuotaFilter` evalúa **ambos** límites — el de la función y el del alumno — y aplica el que se agote primero. El body del 429 incluye `"scope": "function"` o `"scope": "student"` según cuál disparó el corte.

## Criterios de Aceptación (CA)

- [ ] **CA1:** Cuando los tokens consumidos en la función `tutor` alcanzan el 100 % del límite diario configurado, el siguiente request a `POST /api/v1/tutor/message` recibe HTTP 429 con cabecera `Retry-After: <segundos>` y body `{"error": "quota_exceeded", "function": "tutor", "retryAfter": <n>, "resetAt": "<ISO-8601>"}`.
- [ ] **CA2:** El campo `Retry-After` indica exactamente los segundos enteros hasta la medianoche UTC del día actual; el test lo verifica con ±5 segundos de tolerancia.
- [ ] **CA3:** Si el proveedor devuelve HTTP 5xx, el servicio reintenta hasta 3 veces con backoff exponencial (1 s, 2 s, 4 s + jitter aleatorio ≤ 500 ms); si todos fallan, devuelve 502 o 503 (nunca 200).
- [ ] **CA4:** El circuit-breaker abre cuando > 50 % de llamadas a una función fallan en una ventana de 60 segundos; mientras está abierto, los requests reciben 503 con `retryAfter: 30` sin intentar llamar al proveedor.
- [ ] **CA5:** Después de que el `Retry-After` expira (o al abrir una nueva ventana diaria), el mismo request se procesa correctamente (HTTP 200 o 202) si hay cuota disponible.
- [ ] **CA6:** Cada 429 emitido queda registrado en `llm_usage_metrics` con tipo `QUOTA_EXCEEDED` y función asociada.
- [ ] **CA_negativo_1:** (caso que debe fallar) Si el proveedor está caído y la cuota también está superada, el servicio no devuelve HTTP 200 en ningún caso; devuelve el error más específico (429 si cuota excedida, 503 si circuito abierto).
- [ ] **CA_negativo_2:** (caso que debe fallar) Si el 429 se devuelve sin la cabecera `Retry-After`, el test de integración falla y el build se rompe (assertion en el test de contrato).
- [ ] **CA7 (extensión por alumno):** Si un alumno tiene un override de `scope=student` con un límite menor al de la función, el 429 se emite al agotar **ese** límite (aunque la función todavía tenga cuota disponible), con `"scope": "student"` en el body.

## BDD

**Qué se prueba:** que el middleware de cuota emite 429 con Retry-After correcto, que los reintentos internos con backoff no producen 200 cuando el proveedor está caído, y que el sistema se recupera tras el período de espera.

### Escenario 1 — Cuota superada → 429 con Retry-After (camino feliz del caso de error controlado)

- **Dado:** que la función `tutor` tiene un límite de 1 000 tokens/día y ya se consumieron 1 000 tokens en la ventana actual
- **Cuando:** un usuario autenticado hace `POST /api/v1/tutor/message` con un mensaje válido
- **Entonces:** el servicio responde HTTP 429 con cabecera `Retry-After` (valor > 0) y body `{"error": "quota_exceeded", "function": "tutor", "retryAfter": <n>, "resetAt": "<ISO-8601-medianoche-UTC>"}` sin llamar al proveedor

### Escenario 2 — Proveedor caído con reintentos → error controlado, no 200 (caso que debe fallar)

- **Dado:** que la función `tutor` tiene cuota disponible y el proveedor de modelos devuelve HTTP 503 en todos los intentos (simulado con WireMock)
- **Cuando:** un usuario autenticado hace `POST /api/v1/tutor/message` con un mensaje válido
- **Entonces:** el servicio reintenta 3 veces con backoff (verificable en logs con timestamps), devuelve HTTP 502 o 503 con body de error estructurado, y nunca devuelve HTTP 200

### Escenario 3 — Request tras expirar Retry-After → procesado correctamente (recuperación)

- **Dado:** que la función `tutor` recibió un 429 (cuota superada), se avanza el reloj del test a la nueva ventana diaria (medianoche UTC + 1 segundo), y hay cuota disponible en la nueva ventana
- **Cuando:** el mismo usuario hace `POST /api/v1/tutor/message` con el mismo mensaje válido
- **Entonces:** el servicio responde HTTP 200 (o 202 si asíncrono) procesando la solicitud correctamente, sin 429 ni 503

## Prototipo

```
// Respuesta 429 — cuota excedida
HTTP/1.1 429 Too Many Requests
Retry-After: 3600
Content-Type: application/json

{
  "error": "quota_exceeded",
  "function": "tutor",
  "retryAfter": 3600,
  "resetAt": "2026-09-14T00:00:00Z"
}

// Respuesta 503 — circuito abierto
HTTP/1.1 503 Service Unavailable
Retry-After: 30
Content-Type: application/json

{
  "error": "circuit_open",
  "function": "tutor",
  "retryAfter": 30,
  "resetAt": "2026-09-13T10:31:00Z"
}

// Flujo de QuotaFilter (pseudocódigo):
QuotaFilter.doFilter(request):
  1. Identificar función por ruta (QuotaRegistry.resolve(path))
  2. Leer límite activo desde QuotaService (caché L1, TTL 60s)
  3. Leer tokens consumidos hoy desde MetricsRepository
  4. Si consumido >= límite → emitir 429 + Retry-After + registrar QUOTA_EXCEEDED
  5. Si consumido < límite → continuar cadena de filtros
  6. Llamada al proveedor con ResilienceDecorator:
       - Backoff: 1s, 2s, 4s (+jitter ≤500ms), max 3 reintentos
       - CircuitBreaker por función: umbral 50 % / ventana 60s / espera 30s
```
