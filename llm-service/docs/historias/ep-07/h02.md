## Descripción (Como / Quiero / Para)

- **Como:** administrador de la plataforma
- **Quiero:** cambiar el límite de cuota de una función (por ejemplo, tutor o evaluador) a través de una llamada API y que el cambio quede registrado con quién lo hizo, cuándo y por qué motivo
- **Para:** poder ajustar la política de uso del proveedor de modelos sin necesidad de redesplegar código y con trazabilidad completa que permita auditorías

> **Extensión (2026-09-13, ver [08 P-12](../../08-decisiones-y-pendientes.md)):** si el back
> office (Tema 12) necesita limitar el uso de IA **por alumno** — cantidad de usos y cantidad de
> tokens, por día —, esta misma historia se extiende con un segundo `scope`. Es una segunda
> dimensión de configuración, no un reemplazo del límite por función.

---

## Notas / Observaciones

- Las cuotas se almacenan en una tabla append-only `llm_quota_policy`; nunca se actualiza un registro existente, solo se inserta uno nuevo con `effective_from` = ahora.
- Cada registro incluye: `scope` (`function` | `student`; por defecto `function` para compatibilidad con lo ya descrito abajo), `function_name`, `student_id` (nulo si `scope=function`; obligatorio si `scope=student`), `limit_tokens_per_day`, `limit_interactions_per_day` (cantidad de usos por día — solo aplica con `scope=student`; con `scope=function` la cantidad de usos sigue siendo el valor global de P-05), `changed_by` (subject del JWT), `changed_at` (timestamp servidor), `reason` (texto libre, obligatorio, mínimo 10 caracteres, máximo 500), `previous_limit` (valor anterior para auditoría).
- El límite activo es el registro con `effective_from` más reciente para esa función (o para esa combinación función + alumno, cuando `scope=student`).
- Los valores permitidos para `limit_tokens_per_day` y `limit_interactions_per_day`: entero positivo > 0 y ≤ 10 000 000 (diez millones) para tokens, ≤ 1 000 para interacciones. Cero, negativo o superior al máximo → 400.
- El campo `reason` es obligatorio. Sin él o con menos de 10 caracteres → 400 con mensaje "El campo reason es obligatorio y debe tener al menos 10 caracteres".
- Solo tokens con scope `ADMIN` pueden modificar cuotas (de función o de alumno). `OPS` solo puede leer. `TEACHER`/`STUDENT` → 403.
- El historial completo de cambios es accesible vía `GET /api/v1/operations/quotas/{function}/history` (paginado, solo ADMIN/OPS); el override por alumno tiene su propio historial en `GET /api/v1/operations/quotas/student/{studentId}/history`.
- El cambio tiene efecto en la siguiente ventana de evaluación de cuota (≤ 1 minuto de propagación).
- La operación es idempotente respecto al contenido: si se envía exactamente el mismo límite y motivo en menos de 60 segundos, el servicio devuelve 200 con el registro existente sin duplicarlo.
- Un override por alumno no reemplaza el límite por función: `QuotaFilter` (ver [h03.md](h03.md)) evalúa ambos y aplica el más estricto.

## Criterios de Aceptación (CA)

- [ ] **CA1:** `PUT /api/v1/operations/quotas/{function}` con token ADMIN, `limit_tokens_per_day` válido (> 0, ≤ 10 000 000) y `reason` de al menos 10 caracteres devuelve HTTP 200 con el registro creado, incluyendo `id`, `changedBy`, `changedAt`, `previousLimit` y `effectiveFrom`.
- [ ] **CA2:** El historial `GET /api/v1/operations/quotas/{function}/history` devuelve todos los cambios en orden cronológico descendente, con todos los campos de auditoría, paginado (máx. 50 por página).
- [ ] **CA3:** El límite activo entra en vigor en ≤ 1 minuto tras el cambio; el endpoint del panel (LLM-S09-H01) refleja el nuevo `quotaLimit` en la siguiente respuesta.
- [ ] **CA4:** La tabla `llm_quota_policy` nunca tiene registros borrados ni actualizados; solo se permiten inserts (verificable por constraint en BD y test de migración).
- [ ] **CA5:** La operación idempotente (mismo límite + mismo motivo dentro de 60 s) devuelve HTTP 200 con el registro existente y no inserta un duplicado.
- [ ] **CA_negativo_1:** (caso que debe fallar) Un request con `limit_tokens_per_day` igual a 0, negativo o superior a 10 000 000 devuelve HTTP 400 con `{"error": "invalid_quota", "detail": "El límite debe ser un entero entre 1 y 10000000"}`.
- [ ] **CA_negativo_2:** (caso que debe fallar) Un request con `reason` ausente o con menos de 10 caracteres devuelve HTTP 400 con `{"error": "missing_reason", "detail": "El campo reason es obligatorio y debe tener al menos 10 caracteres"}`.
- [ ] **CA_negativo_3:** (caso que debe fallar) Un token con scope `TEACHER` intenta modificar una cuota y recibe HTTP 403 con `{"error": "forbidden", "requiredScope": "ADMIN"}`.
- [ ] **CA6 (extensión por alumno):** `PUT /api/v1/operations/quotas/student/{studentId}` con token `ADMIN`, `limit_tokens_per_day` y/o `limit_interactions_per_day` válidos y `reason` de al menos 10 caracteres devuelve HTTP 200 con el registro creado (`scope: "student"`, `studentId`, ambos límites, `changedBy`, `changedAt`, `effectiveFrom`). Sin `studentId` en la ruta, o con un `studentId` que no existe, devuelve 400.

## BDD

**Qué se prueba:** que el administrador puede cambiar límites de cuota con trazabilidad completa, que valores inválidos y falta de justificación son rechazados, y que roles no autorizados no pueden modificar cuotas.

### Escenario 1 — ADMIN sube el límite del tutor con motivo válido (camino feliz)

- **Dado:** que existe un token JWT con scope `ADMIN` y la función `tutor` tiene un límite vigente de 500 000 tokens/día
- **Cuando:** el ADMIN hace `PUT /api/v1/operations/quotas/tutor` con body `{"limit_tokens_per_day": 750000, "reason": "Incremento por inicio de ciclo lectivo septiembre 2026"}`
- **Entonces:** el servicio responde HTTP 200 con `{"function": "tutor", "limit_tokens_per_day": 750000, "previousLimit": 500000, "changedBy": "<subject-del-jwt>", "changedAt": "<timestamp>", "reason": "...", "effectiveFrom": "<timestamp>"}` y el nuevo registro aparece en el historial

### Escenario 2 — Cambio sin campo reason (caso que debe fallar)

- **Dado:** que existe un token JWT con scope `ADMIN`
- **Cuando:** el ADMIN hace `PUT /api/v1/operations/quotas/tutor` con body `{"limit_tokens_per_day": 750000}` (sin `reason`)
- **Entonces:** el servicio responde HTTP 400 con `{"error": "missing_reason", "detail": "El campo reason es obligatorio y debe tener al menos 10 caracteres"}` y no se inserta ningún registro en `llm_quota_policy`

### Escenario 3 — Docente intenta cambiar una cuota (caso que debe fallar)

- **Dado:** que existe un token JWT con scope `TEACHER`
- **Cuando:** el docente hace `PUT /api/v1/operations/quotas/tutor` con body válido
- **Entonces:** el servicio responde HTTP 403 con `{"error": "forbidden", "requiredScope": "ADMIN"}` y el límite vigente no cambia

### Escenario 4 — ADMIN fija un límite por alumno (extensión, camino feliz)

- **Dado:** que existe un token JWT con scope `ADMIN` y el alumno `b1e2c3d4-0004-4a00-8000-000000000004` no tiene override propio (usa el límite global de la función)
- **Cuando:** el ADMIN hace `PUT /api/v1/operations/quotas/student/b1e2c3d4-0004-4a00-8000-000000000004` con body `{"limit_interactions_per_day": 20, "limit_tokens_per_day": 40000, "reason": "Seguimiento por uso atípico detectado por el docente"}`
- **Entonces:** el servicio responde HTTP 200 con `{"scope": "student", "studentId": "b1e2c3d4-0004-4a00-8000-000000000004", "limit_interactions_per_day": 20, "limit_tokens_per_day": 40000, "changedBy": "<subject-del-jwt>", "changedAt": "<timestamp>", "reason": "...", "effectiveFrom": "<timestamp>"}`, y desde ese momento ese alumno queda sujeto al límite que sea más estricto entre este override y el límite por función (ver [h03.md](h03.md))
