## Qué hay en el código

- `llm-service/compose.yaml` (backend aislado, solo Postgres + `llm-service`) y
  `llm-service/compose.workbench.yaml` (demo con `llm-workbench` en `:4200`) arrancan con
  `docker compose up --build`.
- `llm-service/compose.debug.yaml` (nuevo, 2026-09-16): overlay que publica `5432:5432` en
  Postgres **solo** para debug local / reproducir CA4 — el compose base no publica ningún puerto
  (ADR-015, [`05-servicios-docker.md`](../../../02-arquitectura-y-plataforma/05-servicios-docker.md)).
- El servicio `postgres` de `compose.yaml` ahora tiene un volumen nombrado
  `llm-postgres-data:/var/lib/postgresql/data` (gap real que sí existía hasta esta sesión — antes
  no había ningún volumen, los datos se perdían en cada `down`).
- `llm-service/.env.example` existe y está commiteado, con las variables del ADR-019
  (`SERVER_PORT`, `SPRING_DATASOURCE_URL/USERNAME/PASSWORD`, `EUREKA_URL`).
- El README documenta y funciona: `docker compose up --build` (dos variantes), `docker compose
  down`, `docker compose ps` (columna STATUS) y `curl .../actuator/health`; se agregó además la
  sub-sección "Persistencia y debug local".
- `llm-service/scripts/smoke-compose.sh` ahora acepta un modo `--cold` que mide el tiempo de
  `docker compose up --build --wait` y lo imprime en su salida.
- **Eureka/Gateway/Kafka:** el compose no los incluye, ni comentados, por decisión explícita de
  [`05-servicios-docker.md`](../../../02-arquitectura-y-plataforma/05-servicios-docker.md) §3
  (simularlos localmente daría una falsa sensación de integración probada). La ficha de H02
  pedía lo contrario (pinnear un Eureka/Gateway "de mentira") — quedó desactualizada respecto a
  esa decisión posterior y se alineó en esta sesión (ver `historias/ep-01/h02.md`,
  "Estrategia de autonomía").

## Veredicto por CA

| CA | Estado | Evidencia |
|---|---|---|
| CA1 — `docker compose up` deja todo *healthy* | 🟢 | `docker compose up --build --wait` en máquina limpia (sin contenedores/volúmenes previos del proyecto): `postgres` y `llm-service` reportan `Healthy`. |
| Persistencia (T1, no es CA propio pero lo pide la ficha) | 🟢 | Se escribió una fila de prueba en Postgres, se corrió `docker compose down` (sin `--volumes`) y `up` de nuevo: la fila sigue. Contraprueba: `docker compose down --volumes` + `up` sí la borra (Flyway migra desde cero). |
| CA2 — README documenta `up`, *health*, `down` | 🟢 | Los tres comandos se ejecutaron tal cual están escritos en el README durante esta verificación. |
| CA3 (negativo) — sin Docker, falla con mensaje claro | 🟢 | Se quitaron los directorios de Docker del `PATH` en una sesión de shell y se corrió `docker compose up`: falló con `docker: command not found` (exit 127), sin crear ningún contenedor (`docker ps -a` sin diferencias antes/después). |
| CA4 (negativo) — puerto ocupado, el error identifica el puerto | 🟢 | Se ocupó el puerto 5432 del host con un contenedor descartable (`nginx:alpine`) y se corrió `docker compose -f compose.yaml -f compose.debug.yaml up`: falló con `Bind for 0.0.0.0:5432 failed: port is already allocated`, nombrando el puerto en conflicto. |
| T7 — arranque en frío medido | 🟢 | `./scripts/smoke-compose.sh --cold`: **19 s** (AMD Ryzen 5 5600X, Windows 11 Pro, 2026-09-16). "Frío" significa sin contenedores/volúmenes/imágenes previos del proyecto (`down --rmi all --volumes --remove-orphans` antes de medir), no una limpieza total de la caché de capas de Docker. |
